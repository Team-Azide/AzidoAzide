# 커밋

사용자가 Git 커밋을 명시적으로 요청했을 때 실행한다.

## 메시지 규칙

- 제목은 `type: 한글 요약` 형식으로 작성한다. 스코프는 생략한다.
- 변경의 주목적에 맞는 타입 하나를 골라 표의 표기대로 적는다.
- 제목에 담기 어려운 이유나 맥락은 한글 본문에 적는다.

| 타입 | 쓰는 경우 | 제목 예시 |
| --- | --- | --- |
| `feat` | 새 기능이나 콘텐츠 추가 | `feat: 프로젝트 설정 추가` |
| `fix` | 오류나 회귀 수정 | `fix: 저장 오류 수정` |
| `docs` | 기획이나 문서 변경 | `docs: 실행 방법 문서 갱신` |
| `chore` | 빌드·패키지·저장소·도구 설정 변경 | `chore: 빌드 옵션 정리` |
| `refactor` | 동작을 유지하는 코드 구조 개선 | `refactor: 설정 읽기 로직 분리` |
| `test` | 테스트나 검증 코드 변경 | `test: 저장 경로 검증 추가` |
| `art` | 아트 에셋이나 시각 리소스 변경 | `art: 설정 아이콘 교체` |

## 작업 절차

1. 현재 브랜치, 작업 트리, 기존 스테이징과 최근 이력을 확인한다.
2. 요청 범위에 해당하는 변경만 고른다. 기존 스테이징과 범위가 충돌하면 보존하고 사용자에게 확인한다.
3. 변경에 필요한 검증을 실행하고 커밋 전에 브랜치, 대상 파일, 메시지, 검증 결과를 보고한다.
4. 대상 경로를 지정해 스테이징하고, 최종 diff와 공백 오류를 확인한 뒤 커밋한다.

## 결과 보고

커밋 해시, 제목과 검증 결과를 알린다. Push는 사용자가 별도로 요청한 경우에만 수행한다.
